## 一、要解决的问题

v1 的每一笔存款和取款都要花掉同一个池子 cell。README 原先把后果写成「每个池子每块最多 1 笔交易」，
这个说法是错的（见下面的实测）：脚本并不限制一个块里有几笔池子交易，
限制来自「每笔交易都必须建在前一笔的池子输出上」。准确的问题是下面三个。

**1. 存款人的签名绑定了池子 cell 的某一个版本。** 这一条从脚本和签名规则就能确定，不需要实验：
存款交易的输入里有池子 cell，存款人的 sighash-all 签名覆盖交易 hash，也就覆盖了「花的是哪一个池子 cell」。
只要别人的交易先花掉了那个 cell，这笔存款就作废，存款人必须回来重新构造、重新签名。
人越多，一笔存款要重签的次数越多，而且每次重签都要求钱包在线。

**2. 取款没有这个问题，但要有人负责重拼。** 取款交易没有签名，证明只绑定 root、收款人、fee。
池子 cell 变了，任何人都能把同一个证明装进一笔新交易里，不用取款人参与。
v1 里没有谁有动力替别人做这件事。

**3. 互不知情的用户会互相顶掉。** 两个人各自基于同一个池子 cell 构造交易，最多成一笔。
要避免就得让所有人都看着交易池里最新的那个池子输出往后接——这要求每个用户都能读到别人尚未打包的交易，
也意味着前面任何一笔被替换或丢弃，后面接着它的交易全部作废。

### 实测：一个块里可以有多笔首尾相接的池子交易

2026-11-18 在测试网上用 `mixer chain --note 3` 验证（v1 的池子、size 构建）：一笔存款和两笔取款，
每一笔都花前一笔尚未上链的池子输出，3 秒内连发，不等出块。**三笔进了同一个区块 23,099,407**，
是块里的第 2、3、4 笔交易，从发出到出块 14–17 秒；用 `get_block_by_number` 和区块浏览器 API 各核对了一遍。

| 交易 | 花的池子 cell | cycles |
| --- | --- | ---: |
| 存款 note 4 `0xc1c39972…` | 链上已有的 `0x114b0f8a…:0` | 12,917,203 |
| 取款 note 3 `0x6b6045e9…` | 上一笔的输出 0（未上链） | 102,690,161 |
| 取款 note 4 `0x8e96c168…` | 上一笔的输出 0（未上链） | 102,461,184 |

第三笔取的正是第一笔刚存进去的 note：它的证明用的根在发送时还不存在于链上。
所以「每块最多 1 笔」不成立；知道前一笔交易内容的人可以一直往后接。

### 节点的规则（读源码，未逐条实测）

对照的是 `nervosnetwork/ckb` master 的 `94a3012`（2026-11-17）；公共节点报告的版本是 0.210.0，
`tx_pool_info` 返回 `min_fee_rate = 1000`、`min_rbf_rate = 1500`。

* **一条链最多 25 笔待打包交易。** 默认 `max_ancestors_count = 25`，一笔交易连同它在交易池里的祖先
  不能超过这个数（`tx-pool/src/component/pool_map.rs`）。实测只接到 3 笔。
* **冲突的交易按手续费替换（RBF）。** `min_rbf_rate > min_fee_rate` 时开启。花同一个 cell 的新交易要顶掉旧的，
  手续费必须不低于「被顶掉的交易**及其所有后代**的手续费之和 + 1,500 shannons/KB × 新交易体积」，
  一次最多顶掉 100 笔，并且新交易不能引入别的未上链输入（`tx-pool/src/pool.rs` 的 `check_rbf`）。
  付不够就被拒绝，旧的留着。
  实验里顺带对「基于已被花掉的旧池子 cell 的取款」做了 dry-run，节点回答可以接受——但读源码后发现
  `test_tx_pool_accept` 不执行替换检查，所以这个 dry-run **不能证明**替换会成功；
  按上面的公式它的 0.01 CKB 手续费远高于门槛（约 0.00016 CKB），真发出去应当会顶掉那笔存款。**真实的替换没有做过。**
* **`max_tx_verify_cycles`（70M）不是准入门槛。** 本地提交和 dry-run 都按共识的 `max_block_cycles`（3.5G）验证
  （`tx-pool/src/process.rs`），转发来的交易只在声明的 cycles 超过 `max_block_cycles` 时才被拒
  （`sync/src/relayer/transactions_process.rs`）。70M 用在别处：区分验证队列里的「大交易」、
  处理孤儿交易、重组后把交易加回交易池时的上限。

这几条把前面的问题 3 说得更准确：互不知情的两个人不是「后到的作废」，而是**出价高的留下**；
后到的那笔如果付得起，会把前面整条链连同所有后代一起顶掉，付不起就被拒。

对方案的影响：聚合者可以把活儿拆成几笔小交易连发（一条链 25 笔以内），不必把所有东西塞进一笔大交易；
但链上任何一环被顶掉，后面的全部要重拼——这只有在交易里**没有用户签名**时才是便宜的，
也就是下面要做的事。

所以要设计的不是「怎样让一个块里能有多笔池子交易」，而是**把存款人的签名和池子 cell 解耦**，
并且**让排队、拼交易这件事有人负责、有钱赚**。

## 二、方案概览

三处改动，互相独立地各解决一件事：

| 改动 | 解决什么 |
| --- | --- |
| **存款意向 cell**：用户把「面额 + 小费」锁进一个带 commitment 的 cell，不碰池子 cell | 存款不再和任何人抢 cell，签一次名就结束 |
| **批量 action**：一笔池子交易里处理任意多个意向和任意多笔取款 | 一次花池子 cell 能办完很多人的事，排队的人不用各自去抢 |
| **池子 Type ID** | 意向 cell 必须能指名「哪一个池子」，v1 的 type script 做不到这一点 |

取款不需要新的链上结构：v1 的取款交易本来就没有签名，证明绑定的是 root、收款人和 fee，
不绑定池子 cell 的某个版本。所以一笔取款天然就是一条链下消息，谁拿到都能把它放进自己构造的交易里。

角色只多一个**聚合者**：任何人都可以当，不需要许可、不需要押金。它收集链上的意向 cell 和链下的取款消息，
拼成一笔池子交易，赚意向里的小费和取款里的 fee。聚合者偷不了钱、改不了收款人，最坏只是不干活——
那时用户自己当自己的聚合者，退化成 v1 的行为。

```
用户 A ──(交易，自己签名)──▶ 意向 cell A ─┐
用户 B ──(交易，自己签名)──▶ 意向 cell B ─┤
                                          ├─▶ 聚合交易 ──▶ 池子 cell'
用户 C ──(链下消息：证明)────────────────┤              ├─▶ 收款 cell C
用户 D ──(链下消息：证明)────────────────┘              └─▶ 收款 cell D
                              池子 cell ──┘
```

## 三、链上结构

### 3.1 池子 type script v2

args（140 字节）：

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| `type_id` | 32 | 建池时必须等于 `blake2b(交易第一个输入 ‖ 池子输出的下标)`，与系统 Type ID 脚本同一规则 |
| `denomination` | 8 | 同 v1 |
| `vk_hash` | 32 | 同 v1 |
| `pool_lock_code_hash` + `hash_type` | 33 | 同 v1 |
| `intent_lock_code_hash` + `hash_type` | 33 | 意向 lock 的代码 |
| `root_history` | 2 | 状态里保留多少个历史根（v1 写死 30） |

`type_id` 让池子的 type script hash 全链唯一：同样的 args 不可能再建出第二个池子 cell
（输入只能被花一次）。这顺带解决了 README 里「没有 Type ID」那一条。

脚本只接受两种交易：建池（本组 0 个输入、1 个输出：`type_id` 正确、状态为空、带池子 lock）和
批量结算（1 个输入、1 个输出，见 3.3）。池子 cell 不能销毁、不能分裂。
`denomination` 和 `root_history` 为 0 的 args 直接拒绝。

状态：与 v1 相同，只是根的环形缓冲区长度取自 args，共 `680 + 32 × root_history` 字节。

### 3.2 意向 lock

意向 cell：`lock` = 意向 lock，没有 type，没有 data，capacity = 面额 + 小费。

args（104 字节）：

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| `pool_type_hash` | 32 | 这笔钱要存进哪个池子（因为有 Type ID，这是唯一的） |
| `commitment` | 32 | 要插入树的叶子 |
| `owner_lock_hash` | 32 | 谁可以把它撤回 |
| `reclaim_since` | 8 | 撤回路径要求的 `since`（相对块数），用户自己选 |

解锁规则，对同一个 lock 组里的所有输入。走哪条路由「池子在不在输入里」决定，不是二选一：

* **成交**（交易的输入里有一个 cell 的 type script hash 等于 `pool_type_hash`）：
  * 那个池子的 args 必须是合法的 v2 args，并且其中的意向 lock（code hash **和** hash type）
    就是本 cell 的 lock 所用的那一个；
  * 本组的每个 cell 都没有 type、没有 data。
* **撤回**（输入里没有这个池子）：
  * 交易的输入里有一个 cell 的 lock hash 等于 `owner_lock_hash`（它的 lock 验证了所有者的签名）；
  * 本组每个输入的 `since` 都是「相对块数」的形式（最高字节 `0x80`），数值不小于 `reclaim_since`。
    绝对高度、按 epoch 或按时间的 `since` 一律不算——它们不能说明这个 cell 已经存在了多少个块。

`owner_lock_hash` 必须指向一个只有所有者能解的 lock。如果它是任何人都能解的，任何人都能撤回。
args 长度不是 104 字节的 cell 说不出所有者是谁，永远解不开。

意向 lock 自己不做任何记账：钱和 commitment 的去向全部由池子 type script 负责（3.3）。
但它**必须确认池子会把自己算进去**，这就是成交路径第一条的来由，也是实现时发现的原设计的一个洞：

> 池子认意向是按「lock 的 code hash + hash type 等于 args 里配置的那一对」。同一份 intent-lock 代码
> 可以用别的 hash type 引用（`data1`、`type`……），那样的 cell 在池子眼里不是意向，不会被记账；
> 而原设计的成交路径只要求「池子在输入里」。于是谁都可以把这样一个 cell 和池子放进同一笔交易，
> 池子不记这笔存款，钱被拿走。这种 cell 只会来自用错 hash type 的钱包，但后果是丢钱。

修正后，这样的 cell 成交路径走不通（退出码 60），只能由所有者撤回。
去掉这条检查重新编译，对应的两个测试会失败（交易被接受）——确认过测试确实在测这件事。
代价是意向 lock 要读池子的 args，和它的布局绑在了一起。

`reclaim_since` 的作用是给聚合者一个确定的窗口：在这之前意向只能成交、不能撤回，
聚合者把它放进交易后不会被所有者抽走而导致整笔交易作废。脚本只执行用户声明的值，
值太小的意向聚合者可以不收——策略留在链下，规则留在链上。

意向 cell 至少占 145 CKB（8 + lock 137），所以 **面额 + 小费 ≥ 145 CKB**。
面额不低于 145 CKB 的池子小费可以任意小；100 CKB 面额的池子做不了意向存款。

### 3.3 批量 action

池子输入的 `WitnessArgs.input_type`：

```
0x02 ‖ w(2, LE) ‖ 取款 × w
取款 = fee(8, LE) ‖ root(32) ‖ nullifierHash(32) ‖ Groth16 证明(128) ‖ len(2, LE) ‖ nullifier 集合证明(len)
```

存款不写在 witness 里。type script 自己数：

* **存款 = 交易里所有「指向我」的意向输入。** 扫描全部输入，lock 的 code hash / hash type 等于 args 里的
  意向 lock、args 长 104 字节且前 32 字节等于本脚本 hash 的，每个算一笔存款，commitment 取自它的 lock args，
  按输入顺序追加进树。设共 `d` 个。
* **取款 = witness 里的 `w` 项**，按顺序处理。第 `i` 笔的收款 cell 是池子输出之后的第 `i` 个输出，
  其余检查与 v1 的单笔取款完全相同（root 在历史里、nullifier 未花、收款 cell 无 type 无 data、
  capacity 恰好是 `面额 − fee`、证明成立）。nullifier 集合依次更新：第 `i` 笔的集合证明针对前 `i−1` 笔之后的根。

然后：

* `d + w ≥ 1`，否则拒绝（不允许空转池子 cell）；
* 取款针对**交易之前**的历史根验证，之后才追加存款；`d ≥ 1` 时记录一个新根，`d = 0` 时不动根；
* 输出状态逐字节等于算出来的新状态；
* 输出 capacity 恰好等于 `输入 capacity + (d − w) × 面额`。

每一笔存款都对应一个被花掉的意向输入，所以「一个意向只记一次账」不需要额外机制——
输入本身就是唯一的。v1 的直接存款（commitment 写在 witness 里、存款人自己花池子 cell）不保留：
想不经过聚合者存款的人先建意向、再自己成交，两笔交易可以不等出块连发（第一节）。
只留一条存款路径，记账规则只有一份。

### 3.4 钱怎么流

* 每个意向 cell 的 capacity 里，`面额` 进池子，余下的是小费；
* 每笔取款从池子放出 `面额`，其中 `面额 − fee` 给收款人，`fee` 留在交易里；
* 小费和 fee 的总和减去矿工费，归构造交易的人。聚合者一般要带一个自己的输入、一个自己的输出来收这笔钱
  （单凭小费凑不出一个 61 CKB 的 cell），并为自己的输入签名。

聚合者不需要垫资：存款的钱来自意向 cell，取款的钱来自池子。

## 四、链下部分

### 4.1 取款消息

```json
{ "pool": "<池子 type script hash>", "root": "…", "nullifier_hash": "…",
  "recipient": { "code_hash": "…", "hash_type": "…", "args": "…" },
  "fee": 1000000, "proof": "…" }
```

内容就是 v1 取款交易里的 action 加上收款 lock，不含任何秘密，也不含 nullifier 集合证明
（那要按交易里的顺序现算，由聚合者负责）。聚合者收到后在链下验一遍证明（主机上毫秒级），
fee 够就排进下一批。

怎么把消息送到聚合者手里不属于共识：最简单是聚合者各自开一个 HTTP 接口。
提交者的 IP 和收款地址会被聚合者看到，这和 Tornado 的 relayer 是同一个问题，同样靠 Tor 之类解决。

### 4.2 聚合者的工作

1. 用索引器按「意向 lock 的 code hash + args 前缀 = 池子 hash」找出所有意向 cell；
   丢掉 commitment 非规范的、capacity 不足 `面额 + 最低小费` 的、带 type 或 data 的、离可撤回时间太近的。
2. 从取款消息里挑出证明有效、root 还在历史里、nullifier 未花的。
3. 从链上（以及交易池里尚未打包的池子交易）算出当前的树和 nullifier 集合，
   排好顺序，算出每笔取款的集合证明和新状态，拼交易，给自己的输入签名，发送。
4. 交易因为某个输入失效而被拒（意向被别人先成交了、nullifier 被别的交易花了、root 出了历史）时，
   去掉那一项重拼。重拼不需要任何用户参与：没有用户签名，也不用重新出证明。

### 4.3 用户的保底路径

* 存款：意向没人理，到期后撤回；或者自己成交自己的意向。
* 取款：自己拼一笔 `d = 0, w = 1` 的交易，和 v1 一样不需要签名、不需要事先有 CKB。

所以聚合者只影响快慢，不影响能不能存取。

## 五、安全性分析

逐条是「攻击者想做的事 → 为什么做不到」。每一条对应的测试列在本节末尾。

**针对意向 cell**

* 花掉意向 cell 但不把 commitment 记进树 → 成交路径要求池子 cell 在输入里；池子 type script 把每个指向它的
  意向输入都记为一笔存款，并要求池子 capacity 相应增加。没有「只取款的 action」可以绕开：存款不是 action 的一部分。
* 用一笔存款抵两个意向（double satisfaction）→ 记账的单位是输入，不是 commitment；
  两个 commitment 相同的意向是两个输入，树里要追加两片叶子，池子要多收两份面额。
* 把意向引到一个冒牌池子 → 意向 args 里是池子的 type script hash，含 Type ID，不可能有第二个。
  参数完全相同的另一个池子也不行：它的 Type ID 不同，hash 就不同。
* 用池子不认的 hash type 引用意向 lock，让 cell 被花掉却不记账 → 意向 lock 在成交路径上核对池子 args
  里配置的正是自己（3.2）。
* 不经所有者同意撤回 → 撤回路径要求所有者的 lock 在同一笔交易里通过验证。
  （所有者的 lock 如果本身是任何人都能解的，那是所有者自己的问题。）
* 抢在聚合交易上链前撤回，让聚合交易作废 → 撤回路径要求相对块数的 `since`，`reclaim_since` 之前
  共识不让这笔交易上链。（脚本强制的是 `since` 的形式和数值，「还没到时间」由共识拒绝；
  本地测试工具只跑脚本，后一半没有测。）
* 意向 cell 上误带了 type script 或 data（比如 UDT）→ 成交路径拒绝，只能撤回，聚合者拿不走。

**针对批量取款**

* 一个收款输出抵两笔取款 → 第 `i` 笔取款只认池子输出后的第 `i` 个输出，位置一一对应；
  同一笔交易里的另一个池子有自己的一段位置，且池子 cell 自己带 type，当不了收款 cell。
* 同一批里把同一个 nullifier 花两次 → 集合是逐笔更新的，第二次时它已经在集合里。
* 聚合者改收款人、抬 fee、少付 → 和 v1 一样，证明绑定了收款 lock 和 fee，收款 capacity 被脚本钉死。
* 聚合者调换批内顺序、丢掉某一项 → 可以，但只影响先后，不影响任何一笔的结果。

**witness 不被签名覆盖**

批量 action 在池子输入的 witness 里，聚合者的签名并不覆盖它（sighash-all 只覆盖自己那组的 witness）。
这不是问题，v1 也是如此：action 的全部效果都体现在输出里——新的树根、新的 nullifier 根、每个收款 cell——
而输出是交易 hash 的一部分。换掉 witness 里的任何一个字节，脚本算出的状态就和输出对不上。

**没有解决的**

* **抢跑聚合者。** 交易里除了聚合者自己的输入输出，其余部分谁都能照抄，把收益换成自己的。
  用户不受影响；聚合者之间是纯粹的手续费竞争。
* **占着池子 cell 捣乱。** 有人可以不停地用更高的手续费替换别人待打包的池子交易。
  按第一节读到的替换规则，每次要付的钱不低于被顶掉的整条链的手续费之和，被挤掉的批次重拼即可；
  但这是共享一个 cell 的方案去不掉的弱点。真实的替换还没有在测试网上做过。
* **用作废拖慢聚合者。** 把同一条取款消息同时交给多个聚合者（或自己直接上链），只有一笔能成，
  其它批次要重拼。每次要真花掉一张 note，成本有下限；重拼便宜。
* 链下消息通道的可用性和隐私（4.1）。
* 可信设置、`verifier-core` 未审计等 v1 的已知问题原样保留。

交易字节里约 4.8 KB 是池子 cell 的状态（输出 data），每笔池子交易都要带一份；
存款的第一笔贵是因为要做满 20 次 Poseidon；之后每笔平均约 0.9 次（约 41.6 万一次），
外加运行一次它自己的意向 lock（约 2.3 万）。

2 笔取款的分段（profile 构建，共 139.6M）：每笔取款 Groth16 约 67.4M、nullifier 集合约 2.2M、
收款检查约 7 千；程序加载、读状态、比对输出合计约 0.27M，整批只付一次；
池子 lock 加测试里聚合者的 lock 约 2.1 万。
4 笔存款的批次里，四个意向 lock 加池子 lock 合计约 11 万，即每个意向 lock 约 2.3 万。

按 1,000 shannons/KB 的最低费率，一笔取款按权重折合约 11.9 KB，最低矿工费约 0.00012 CKB；
1,000 笔存款约 0.40G cycles（块的 12%）、44 KB（**估算**，由上表外推，没有实际跑过 1,000 笔的批次）。

限制吞吐的是取款的 Groth16 验证，存款几乎不占资源。一个现实的批次（8 笔取款 + 8 笔存款）
是 0.57G cycles，占块的 16%。

「50 笔」是脚本层面的上限：这样一笔交易按权重折合 594 KB，一个块（597 KB）里放不下别的东西。
交易池另有一个单笔交易 512 KB 的上限（`TRANSACTION_SIZE_LIMIT`），它按序列化后的字节数算，
不按权重算，这笔交易只有 29 KB，不受它限制。
它能不能被节点接受、转发和打包没有测过，下一段的保留意见对它尤其适用。

**未验证：单笔交易能有多大。** 测试网上验证过的最大单笔交易是 1.03 亿 cycles。8 笔取款的批次是
5.6 亿 cycles；按第一节读到的源码，准入和转发的上限都是 `max_block_cycles`，这么大的交易不会被策略拒绝，
但它在节点之间转发、验证耗时、被矿工选中的实际表现没有测过。实现第 2 步时要先在测试网上
从 2 笔取款开始逐步加大。如果大交易表现不好，退路是已经实测过的：每笔交易放 1–2 笔取款，
首尾相接地连发，一条链 25 笔以内。

两种做法的取舍：一笔大交易只付一次池子脚本的固定开销（很小），被顶掉时整批重拼；
多笔小交易可以边收边发，但后面的交易依赖前面每一笔都不被顶掉。聚合者可以自己选，脚本不用区分。

固定成本：

* 意向 lock 要多部署一份代码：23.6–24.0 KB，即约 2.4 万 CKB（**实测**体积）。逻辑很少，
  体积主要是 `ckb-std` 的运行时；值得专门压。
* pool-type-v2 比 v1 大约 5–6 KB（size 构建 127,368 对 121,400 字节）。
* 池子 cell 变大。`root_history = 128` 时状态 4,776 字节，池子 cell 占 5,022 CKB（**实测**；v1 是 1,819 CKB）；
  保持 30 时是 1,886 CKB（按字节数算出，没有建过这样的池子）。
* 每个待成交的意向临时占用 145 CKB 以上（**实测** 145 CKB），成交或撤回时全部释放。

### 历史根要留多少个

一笔含存款的池子交易记录一个根。聚合之后根的消耗速度从「每笔存款一个」变成「每个批次一个」，
但批次可以很密：每块一批时，30 个根只有约 4 分钟（测试网实测出块间隔约 7.8 秒），
证明从生成、送到聚合者到上链必须在这之内完成。128 个根约 17 分钟，256 个约 33 分钟，
代价是每个根多锁 32 CKB。建议 128，并让聚合者每块至多发一个含存款的批次。

### 可选优化：批量验证 Groth16（未验证）

`w` 个证明可以用随机线性组合合并成一次配对检查：每个证明只剩 1 次 Miller loop（整批另有 3 次共用的），
final exponentiation 从 `w` 次降到 1 次，代价是每个证明多几次 G1 标量乘。
随机数由全部证明和公开输入的哈希导出。理论上每多一笔取款的边际成本能降到现在的几分之一，
一个块能装的取款数相应上升。这需要改 `verifier-core`（本来就未经审计的代码），
实际能省多少没有测过，不在第一阶段范围内。

## 七、实施步骤

1. **脚本和核心库（已完成）**：批量 action 的编解码和可变长度的根历史（`mixer-core-v2`）；
   `pool-type-v2`（Type ID、扫描意向输入、批量取款）；`intent-lock`。本地测试覆盖第五节的每一条，
   第六节标为「估算」的数字已重测。
2. **聚合者（未开始）**：在 `tools/testnet` 里加 `mixer intent`（建意向）、`mixer aggregate`（拼一批并发送）、
   取款消息的文件格式；在测试网上跑多个意向 + 多笔取款的批次，以及两个聚合者互相竞争的情形。
3. **可选**：批量验证 Groth16 的原型和测量。

v2 是新的 type script，和 v1 的池子互不相干：v1 池子继续按 v1 的规则工作，里面的 note 不会自动迁移。
电路和验证密钥不用改。

## 八、考虑过但没有选的

* **不改脚本，只靠首尾相接地发交易。** 节点允许（第一节，已实测），但只对取款有用：
  存款人的签名绑定了池子 cell 的版本，前面任何一笔被顶掉就得重签。
* **把树拆成多个池子 cell（分片）。** 能真正并行，但每个分片的匿名集合变小，
  要保持一个大匿名集合就得再加一层「根的根」，电路要改，复杂度高一个量级。
* **链上的取款意向 cell。** 取款人得先有 CKB 才能建 cell，正好丢掉了「取款不需要事先有钱」这个性质。
* **意向 lock 自己核对池子的 action。** 可以不改 pool-type，但意向 lock 要解析池子的 witness，
  两个脚本对同一份数据各有一套理解；而批量取款无论如何都要改 pool-type。
* **保留 v1 的直接存款。** 多一条存款路径，换来的只是自助存款少发一笔交易。
